# Prototype replay (superseded)

**Superseded by the engine in `hanabi_data/`** (`docs/representation.md` §5.1), which reproduces this
prototype's output exactly at every position of the example games (`tests/test_parity.py`). It is kept
only as the reference for that test. Its shortcomings, listed below, are what the engine fixes.

`replay.py` replays one hanab.live-format export and prints the v0 decision record
(`docs/representation.md` §7) for a single turn.

```bash
# Decision record for game 78921, UI "Turn 4" (0-based turn argument = actions already taken)
python3 prototype/replay.py prototype/examples/export_78921.json 3 --pretty
```

| File | What it is |
|---|---|
| `replay.py` | The prototype |
| `examples/export_78921.json` | `new.playhanabi.com/export/78921`, unchanged (the game in screenshots 1–2) |
| `examples/export_78822.json` | `new.playhanabi.com/export/78822`, unchanged (3 players; the game in screenshot 3) |
| `examples/decision_78921_turn4.json` | The decision record for turn 4, embedded in the design doc. Now generated by `python3 -m hanabi_data decision prototype/examples/export_78921.json 4 --pretty` (the prototype's output plus the full `meta`) |
| `examples/export_78922.json` | `new.playhanabi.com/export/78922`, unchanged (2 players, No Variant, default options): the test game captured live as table 43267 |
| `examples/live_43267_player0_*.txt` | That game's `gameActionList` websocket messages as seat 0 (harikari.live) received them: after the deal, after turns 3 and 10 (own cards hidden), and after the end (unhidden). One message per file, verbatim. See `docs/representation.md` §3.4 |

## What it has been checked against

Two games, both checked by eye against screenshots:
- **78921** (2 players, 6 suits, 11 actions, ends in a strikeout). At turns 4 and 10, the score, clue count,
  strikes, deck count, pace, stacks, hand contents, slot positions and clue touches match screenshots 1 and 2.
- **78822** (3 players, 6 suits, 9 actions). At turn 6 the same fields, plus the discard pile, match
  screenshot 3.

Both games also match hanab.live's own reducer at every position (`review/oracle`, run by
`review/server/bundle.py`).

`decision_record(export, turn, viewer=None)` can also give any seat's view, not only the acting
player's (used for the review bundle).

Nothing else has been tested: no 4–5 player games, no 5-suit games, no game that runs past the end of the
deck.

## Known shortcomings

**Rules and validation**
- **No legality checks.** It trusts the export. It doesn't check that the played card is in the actor's
  hand, that a clue touches ≥1 card, that clue tokens stay within 0–8, or that nobody discards at 8 clues.
  An illegal action in an export produces a wrong record silently.
- **No end-of-game detection.** It doesn't recognise a strikeout, an All or Nothing fail (max score no
  longer reachable), an All or Nothing softlock, or a win, and it doesn't stop there. It simply stops when
  the actions run out.
- **End-game actions (types 4/5) are not supported.** It raises `NotImplementedError` rather than
  misreading them as clues.
- **`options.startingPlayer` is not supported.** It assumes seat 0 moves first and raises if the option is
  present.
- **Settings are hardcoded:** `all_or_nothing: true`, `server: new.playhanabi.com` and the hand-size table.
  It ignores `options` (One Extra Card / One Less Card etc. would be wrong). The number of suits is taken
  from the deck, not the variant name.
- **`legal` ignores All or Nothing edge cases.** It hasn't been checked for empty hands after the deck runs
  out, where only clues are possible, or for the softlock state.
- ~~A turn index past the last action fails~~ Fixed 2026-09-23: `turn == len(actions)` gives the final
  position, with no label.

**Decision-record content**
- **`meta` is incomplete.** Only `players` and `raw_action` are filled in. The filtering fields in
  `docs/representation.md` §7.3 are missing: `actor`, `datetime`, `final_score`, `won`, `end_condition`,
  `total_turns`, `turns_to_end` and `label_effect`. None of them can be computed without end-of-game
  detection and the history-page listing.
- **`know` is clue-only by design** (open question Q6). `pace` now matches hanab.live (reachable max
  score; `null` once the deck is empty), but whether it suits All or Nothing is still open (question
  Q4).
- **No GameRecord layer.** It reads a raw export directly, not the `hanabi-game/v0` wrapper from §6.

**Engineering**
- **Replays from turn 0 for every record.** Generating a whole game costs O(T²). The real engine should
  replay once and emit every turn.
- Loosely structured dicts, not typed models. No tests. The CLI takes only one game and one turn.
